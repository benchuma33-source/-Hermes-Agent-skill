# 语音摘要 + 文字详情 双轨输出

让语音助手只念「能听懂的部分」，其余内容留在屏幕上。

## When to Use / 何时用

用户开着语音模式、或明确要求「读出来 / 语音输出」时。

纯文字对话不强制。但一旦用户要求了，**本会话后续都保持这个格式**——
断断续续会让用户不知道什么时候有声音。

## 输出格式

每条回复必须是两段，顺序不能颠倒：

```markdown
> 🔊 <摘要：2~4 句口语，15 秒内能读完，不带任何符号>

---

<详细内容：表格、代码、路径、清单，正常 markdown>
```

摘要用 blockquote（`> `）标记，便于程序提取送给 TTS。
分隔线 `---` 之后是详情。

## 摘要怎么写

**必须**
- 2~4 句，约 80 字，15 秒内能读完
- 口语化，用能说出口的词
- 先说结论或状态，再说关键原因，最后指路「细节在下面」
- 中文标点，不用 markdown 符号

**禁止出现在摘要里**
- 表格、代码块、命令行、文件路径、URL
- 十六进制、版本号、堆叠的精确数字
- 括号嵌套、斜杠分隔的枚举
- 表情符号（TTS 会读成「笑脸」）

**该说什么**
- 做成了没有，卡在哪里
- 为什么，一句话
- 用户下一步该干什么

## 详情怎么写

正常 markdown，不加限制。表格、代码、路径、数据都放这里。
用户会看，不会听。

## 朗读怎么做

写完回复后调用：

```
text_to_speech(text=<摘要原文，去掉 > 和 🔊 标记>, output_path=<临时路径>)
```

**只传摘要，不传详情。** 这正是双轨的意义。

### 音频文件必须删掉

生成后播完立即删除，不留在磁盘：

```bash
F=/tmp/spoken_$(date +%s).mp3
afplay "$F" && rm -f "$F"
```

不要输出到项目目录或桌面，只走 `/tmp`。
长期积累会占几百 MB 且没人清。

## 判定示例

### 好摘要

> 🔊 老师，语音服务接好了。合成用本地模型，识别走云端接口。中间踩了四个坑，主要是音频格式的问题，细节在下面。

### 坏摘要

> 🔊 老师，语音服务接好了，provider 设成了 breeze，识别设成了 qwen，实时率是零点八二，文件在盘符深路径下，详见文档的踩坑章节。

问题：配置键名、数字、文件位置都是只能看不能听的。念出来用户一脸懵。

## 懒人判定法

写完摘要后自问一句：**这段话念出来，用户闭着眼睛能听懂吗？**

听不懂就是混进了只能看的内容，重写。

## 不适用的情况

**默认每条都读，包括短确认。** 唯一例外：用户说「别读了」「安静点」，
则本回合及后续停止朗读，直到用户再要求。

以下情况摘要要**改写**而不是不写：

- 回复本身是表格或数据 → 摘要说「详情是一张对比表，重点结论是某样东西」，不念表
- 极短的确认 → 用一句话摘要即可，但仍要读

## 落地检查

- [ ] 摘要块在最前，用 `> 🔊` 开头
- [ ] 摘要 2~4 句、无符号、能闭眼听懂
- [ ] `---` 分隔，详情在后
- [ ] 已调用 text_to_speech 且只传摘要
- [ ] 音频文件播完已删
